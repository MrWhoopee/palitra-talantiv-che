# Палітра талантів

Сайт для запису на заняття музичної студії в Черкасах (вокал, фортепіано,
гітара, укулеле). Turborepo-монорепозиторій: Next.js фронтенд, Express API
на Prisma/PostgreSQL і спільні пакети з типами та валідацією.

## Налаштування

Виконувати саме в цьому порядку — інакше `pnpm dev` чи `pnpm typecheck`
впадуть з незрозумілою помилкою.

1. Встановити залежності:

   ```sh
   pnpm install
   ```

2. Скопіювати файли оточення (жоден `.env` не лежить у репозиторії):

   ```sh
   cp .env.example .env
   cp apps/api/.env.example apps/api/.env
   cp apps/web/.env.example apps/web/.env
   ```

3. Згенерувати `JWT_SECRET` і вписати його в `apps/api/.env` замість
   заглушки. Дефолту в нього немає навмисно: секрет із прикладу поїхав би
   у продакшн непоміченим, і тоді будь-хто зміг би підробити токен доступу.

   ```sh
   node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
   ```

4. Підняти PostgreSQL і Mailpit у Docker:

   ```sh
   pnpm db:up
   ```

5. Згенерувати Prisma Client (каталог `apps/api/src/generated/` не
   комітиться в git — без цього кроку `pnpm typecheck` не пройде):

   ```sh
   pnpm --filter @palitra/api db:generate
   ```

6. Накотити міграції на базу:

   ```sh
   pnpm --filter @palitra/api db:deploy
   ```

7. Наповнити базу демо-даними (8 викладачів з графіками, 2 локації, 4 напрями,
   тарифи, дві групи зі складом і заявкою, абонемент, учні та адмін). Без цього
   жоден екран запису нема чим наповнити:

   ```sh
   pnpm --filter @palitra/api db:seed
   ```

   Скрипт ідемпотентний — його можна запускати повторно. Пароль усіх демо-акаунтів
   `palitra-demo-2026`, адмін `admin@palitra-talantiv.local`, учень
   `student@palitra-talantiv.local`. У продакшні він відмовляється працювати.

## Запуск

Підняти веб і API одночасно (Turborepo запускає обидва `dev`-скрипти):

```sh
pnpm dev
```

Інші корисні команди з кореня репозиторію:

```sh
pnpm verify          # усе, що робить CI, однією командою
pnpm build           # зібрати всі застосунки й пакети
pnpm lint            # ESLint по всьому монорепозиторію
pnpm typecheck       # tsc --noEmit по всіх пакетах
pnpm test            # усі тести (vitest)
pnpm format:check    # перевірка форматування Prettier
pnpm run audit       # критичні вразливості у прод-залежностях
pnpm db:down         # зупинити Docker-контейнери
```

`pnpm run audit` (саме `run` — інакше запуститься вбудована команда pnpm)
перевіряє лише **критичні** вразливості й лише в прод-залежностях: це ворота,
і вони мають зачинятися рідко. Повний перелік відомих порад друкує
`pnpm audit --audit-level=low` — у CI він теж є, але не блокує збірку. Зараз
там `deepmerge-ts`, до якого ми дістаємось тільки через CLI Prisma: полагодити
його без релізу Prisma неможливо, а в рантаймі він не працює.

**Windows:** `pnpm dev` через turbo у фоновому процесі губить stdio у `tsx watch` —
API стартує, але не слухає порт. В інтерактивному терміналі все гаразд; для
скриптів запускати застосунки окремо (`pnpm --filter @palitra/api dev` і
`pnpm --filter @palitra/web dev`).

## Робочий процес

`main` і `dev` захищені: прямий push і force-push відхиляються, зміни йдуть
через pull request. Гілка для роботи, PR у `dev`, звідти `dev → main`.

```sh
git switch -c feat/opys-zminy
# ...робота...
gh pr create --base dev
```

**Апрув.** PR потребує одного схвалення. Виняток — власник репозиторію (роль
`admin`): він у списку `bypass_actors` правила й мержить свої PR без апруву,
але прямий push закритий і йому теж. Колаборатор із роллю `write` схвалення
потребує завжди.

**Обов'язкова перевірка — `verify / checks`.** Ім'я саме таке, бо reusable
workflow звітує як `<джоб-виклик> / <джоб-усередині>`. Перейменування будь-якої
з двох частин зробить PR незмержуваними: правило чекатиме на перевірку, якої
більше ніхто не надсилає.

**Сама послідовність перевірок живе в
[MrWhoopee/gh-workflows](https://github.com/MrWhoopee/gh-workflows)** — щоб
змінити те, що означає «перевірено», в одному місці, а не в кожному
репозиторії. Тут лишається те, що належить проєкту: Postgres, змінні оточення
й міграції. Джоб, який викликає reusable workflow, не може мати власних
`services`, тому база в CI піднімається з нашого ж `docker-compose.yml` — заодно
CI і локальна розробка не розходяться на два різні описи бази.

Перед PR корисно прогнати те саме локально: `pnpm verify`.

## Авторизація

Реєстрація, вхід і відновлення пароля живуть на сторінках `/register`,
`/login`, `/forgot-password`; листи з посиланнями ведуть на `/verify-email`
і `/reset-password`. Кабінет — `/cabinet`, закритий для неавторизованих.

Листи в розробці нікуди не йдуть — їх перехоплює Mailpit, дивитися на
<http://localhost:8025>.

**Токени.** API віддає пару «access (15 хв) + refresh (30 днів)» у тілі
відповіді, бо майбутньому застосунку на React Native потрібні саме токени.
Веб їх у JavaScript не тримає: `proxy.ts` кладе обидва в httpOnly-кукі, тож
XSS до них не дістанеться. Refresh ротується при кожному оновленні, а
повторне використання вже обміняного токена гасить усі сесії користувача.

**Тестова база.** Інтеграційні тести працюють на справжньому Postgres — на
базі `palitra_test`, яку `pnpm test` створює й мігрує сам. Її ім'я
виводиться з `DATABASE_URL`, тому окремої змінної не потрібно.

## Запис на заняття

Публічні сторінки `/teachers` і `/teachers/:id` показують викладачів і вільний
час; запис відбувається просто з календаря. Кабінет `/cabinet` показує заняття
обом сторонам: учень скасовує свої, викладач підтверджує й позначає результат.
`/cabinet/schedule` — робочі правила й відсутності викладача.

**Час.** Усе зберігається в UTC, а робочі правила й розклад груп — як локальний
час доби плюс день тижня. Розгортання в конкретні дати відбувається в поясі `Europe/Kyiv`,
інакше розклад зсувався б на годину двічі на рік. Уся ця арифметика зібрана в
чистій функції `computeFreeSlots` (`apps/api/src/modules/availability/`).

**Подвійне бронювання** неможливе фізично: за це відповідає exclusion constraint
`lesson_no_overlap` у базі, а не перевірка в коді. Сервіс ловить відмову й
повертає `409 SLOT_TAKEN`.

## Абонементи й групи

**Абонемент** — пакет індивідуальних занять з одним викладачем. Видає його
адміністратор за тарифом, тож кількість занять і ціна беруться з тарифу, а не
вводяться вдруге. Бронювання не списує заняття, але резервує його: забронювати
можна, поки `lessonsUsed + заброньовані < lessonsTotal`. Списання відбувається,
коли викладач позначає заняття проведеним або пропущеним — і коли заняття
скасовують менш ніж за добу до початку (у викладача для цього є окрема кнопка
«Скасувати без списання»).

**Групи** живуть на `/groups` і `/groups/:id`; учень подає заявку, і місце
тримається, поки викладач її розглядає. Розклад групи розгортається в реальні
заняття — саме тому групова зустріч займає викладачеві час так само, як
індивідуальна. Викладач веде групу на `/cabinet/groups/:id`, а журнал
відвідуваності відкривається на кожне заняття окремо.

Якщо якась зустріч не вміщується (у викладача вже є заняття на цю годину),
група все одно зберігається, а форма перелічує пропущені дати.

## Публічний сайт

Сайт живе у трьох оболонках-route-групах: `(site)` — бренд-хедер і футер,
`(cabinet)` — той самий хедер плюс смуга розділів кабінету, `(auth)` — знак і
форма. URL від цього не змінилися.

Публічні сторінки: `/`, `/about`, `/teachers`, `/directions`, `/groups`,
`/events`, `/gallery`, `/achievements`, `/contacts`, `/rules`. Чотири контентні
моделі — події, галерея, відгуки, досягнення — лежать у базі й віддаються
модулем `content` тільки на читання; редагування з'явиться з адмінкою в етапі 6.

**Смуга плеєра зі знака — не оздоба.** Компонент `Track` з'являється лише там,
де є час: тривалість заняття в тарифі, чотири напрями в хіро, подія від початку
до кінця. Кнопки ◀ ⏸ ▶ теж працюють — ними гортається афіша: архів, усі,
найближчі. Правило варте того, щоб його тримати: смуга під заголовком заради
краси вбиває єдину ідею, яка є у знака.

**Порожня секція не рендериться.** Блок «Найближчі події» зникає, поки подій
немає. Сторінка, яка є в меню й зникнути не може, віддає чесний стан із дією.
Відгуки й перемоги не вигадуються навіть у демо: у сіді в них явно тестові
імена.

**Вигляд** зібраний зі спеки етапу 5: холодне тло `#F1F1F9`, фіолетовий
`#7546D0`, темна хвоя `#3A5B4A` для всього, що вимірює час, і помаранчевий
`#F08A2C` — виключно як заливка головної кнопки, ніколи як текст. Токени — в
`apps/web/src/styles/tokens.css`.

## SEO

`generateMetadata` на кожній сторінці, `sitemap.ts` і `robots.ts` засобами App
Router, структуровані дані `MusicSchool` на головній і в контактах та `Event`
на сторінці події. У sitemap потрапляють лише опубліковані записи — не тому, що
там окремий фільтр, а тому що ендпоінти неопублікованого не віддають.

OG-картку малює `opengraph-image.tsx` через `next/og`: знак на тлі `--pt-paper`,
1200×630 PNG. Написи на ній латиницею: у шрифт, який next/og носить із собою,
кирилиця не входить, і український рядок вийшов би рядом порожніх квадратів.

**`NEXT_PUBLIC_SITE_URL` треба задати саме на збірці.** З нього будуються
канонічні посилання, sitemap і структуровані дані, а статичні сторінки
запікають його в HTML під час `next build` — підставити змінну на старті
контейнера вже пізно.

## Порти

| Сервіс         | Порт |
| -------------- | ---- |
| Web (Next.js)  | 3000 |
| API (Express)  | 4000 |
| PostgreSQL     | 5433 |
| Mailpit (UI)   | 8025 |
| Mailpit (SMTP) | 1025 |

**Чому PostgreSQL на 5433, а не 5432**: це навмисний вибір. Порт 5432 часто
вже зайнятий локальним сервісом PostgreSQL на машині розробника — 5433
дозволяє контейнеру співіснувати з ним без конфліктів. Не повертайте цей
порт назад на 5432.
