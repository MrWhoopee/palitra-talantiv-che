Етап робився інлайново, без окремого плану. Цей документ замінює план.

## 1. Що зроблено

Критерій зі спеки — «наскрізний сценарій: бронь → підтвердження → проведено» — виконано й
перевірено двічі: через HTTP на живому API та в браузері через інтерфейс.

Прогін через API (реальні дані сіду):

```
register 201
book 201 PENDING TRIAL
slot gone from offer: True
double book refused: 403 EMAIL_NOT_VERIFIED
teacher login 200
confirm 200 CONFIRMED
complete before it starts: 422 INVALID_LESSON_STATUS
complete after it started: 200 COMPLETED
complete twice: 422 INVALID_LESSON_STATUS
```

Прогін у браузері: учень обрав тариф і час на сторінці викладача → заявка з'явилась у його
кабінеті зі статусом «Очікує підтвердження» → викладач увійшов, натиснув «Підтвердити» →
статус змінився на «Підтверджено». Окремо перевірено, що додана в кабінеті відпустка викладача
вирізає з публічного календаря саме ті дні, а заброньована година зникає з переліку вільних.

| Вимога етапу              | Стан                                                              |
| ------------------------- | ----------------------------------------------------------------- |
| Exclusion constraint      | ✓ `lesson_no_overlap`, з тестом просто в базу                      |
| Пробне заняття            | ✓ одне на учня назавжди, скасування повертає право                 |
| Разове заняття            | ✓ тривалість із тарифу                                             |
| Кабінет учня              | ✓ найближчі, історія, скасування з правилом 24 годин               |
| Підтвердження викладачем  | ✓ плюс «проведено» / «не прийшов»                                  |
| Скасування                | ✓ обома сторонами, з причиною і листом іншій стороні               |
| Кабінет викладача         | ✓ заявки, свій графік, робочі правила й відсутності                |

## 2. Модель даних

Міграція `20260813195455_add_lessons_and_price_plans`.

| Модель      | Ключові поля                                                                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `PricePlan` | directionId, name, lessonsCount, durationMinutes, format (`INDIVIDUAL`/`GROUP`), priceUah, isActive, sortOrder                  |
| `Lesson`    | teacherId, studentId, locationId, pricePlanId?, startsAt, endsAt, durationMinutes, kind, status, cancelledById?, cancelReason? |

Статуси: `PENDING` → `CONFIRMED` → `COMPLETED` / `CANCELLED` / `NO_SHOW`.
Види: `TRIAL`, `SINGLE`, `SUBSCRIPTION` (третій наповниться на етапі 4).

### Захист від подвійного бронювання

```sql
ALTER TABLE "Lesson"
  ADD CONSTRAINT lesson_no_overlap
  EXCLUDE USING gist (
    "teacherId" WITH =,
    tstzrange("startsAt", "endsAt") WITH &&
  ) WHERE (status IN ('PENDING', 'CONFIRMED'));
```

Перевірка «чи вільний слот» у застосунку завжди має вікно гонки: двоє батьків тиснуть
«Записатись» в одну секунду, обидва читають «вільно», обидва пишуть. Constraint робить другий
запис фізично неможливим — сервіс ловить SQLSTATE `23P01` і повертає `409 SLOT_TAKEN`.

**Скасовані, проведені й `NO_SHOW` заняття навмисно виключені з обмеження**: вони більше не
тримають час викладача, і година знову стає доступною. Той самий набір статусів читає
`computeFreeSlots` — щоб те, що показує календар, і те, що приймає база, не могли розійтися.

`endsAt` зберігається поряд із `durationMinutes`, хоч і виводиться з нього: constraint індексує
`tstzrange("startsAt", "endsAt")`, а обчислюване в запиті значення індекс не покрив би.
Узгодженість тримається тим, що в `Lesson` пише виключно сервіс бронювання.

### Що відкладено до етапу 4

`studentId` поки **NOT NULL**, а замість XOR зі спеки стоїть `CHECK ("studentId" IS NOT NULL)`.
Групи ще не існує, тож колонки `groupId` немає. Етап 4 зніме NOT NULL, додасть `groupId` і
замінить обмеження на справжній XOR — це розширення типу колонки, найбезпечніший вид міграції.
Альтернатива (одразу nullable) означала б `lesson.studentId!` у кожному рядку сервісу заради
гарантії, яку зараз і так дає база.

## 3. Ендпоінти

| Метод | Шлях                       | Успіх | Хто                                     |
| ----- | -------------------------- | ----- | --------------------------------------- |
| GET   | `/price-plans`             | 200   | публічний, лише активні тарифи          |
| POST  | `/bookings`                | 201   | будь-який авторизований                 |
| GET   | `/me/lessons`              | 200   | свої заняття з обох боків               |
| POST  | `/lessons/:id/confirm`     | 200   | викладач цього заняття або адмін        |
| POST  | `/lessons/:id/cancel`      | 200   | учень (>24 год), викладач, адмін        |
| POST  | `/lessons/:id/complete`    | 200   | викладач цього заняття або адмін        |
| POST  | `/lessons/:id/no-show`     | 200   | викладач цього заняття або адмін        |

Нові коди помилок у `packages/shared`: `EMAIL_NOT_VERIFIED` (403), `INVALID_LESSON_STATUS` (422).
Решта — уже передбачені спекою: `SLOT_TAKEN`, `TRIAL_ALREADY_USED`, `TOO_LATE_TO_CANCEL`,
`OUTSIDE_BOOKING_HORIZON`, `NOT_TEACHER_OWNED`.

**`GET /me/lessons` — один запит для обох кабінетів**: віддає заняття, стороною яких є
запитувач, з якого боку він у них не був би. Учень бачить свої, викладач — свої; сторонній —
порожній список. Телефон учня входить у відповідь, бо він потрібен викладачеві, а побачити
заняття може лише його сторона.

## 4. Бізнес-правила й де вони живуть

Усі — в сервісі, жодного лише в інтерфейсі. Кнопка ховається, але сервер перевіряє незалежно:
для майбутньої мобілки це єдиний захист, а API відкрите й без неї.

| Правило                        | Реалізація                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------- |
| Пробне — одне на учня назавжди | запит `kind=TRIAL AND status != CANCELLED`, без окремого прапорця в `User`        |
| Скасоване пробне повертає право | випливає з умови вище: скасоване не рахується                                     |
| Тривалість — із тарифу          | `plan.durationMinutes`; поле в запиті ігнорується (є тест)                        |
| Горизонт 4 тижні                | `SCHEDULING.bookingHorizonDays`, той самий, що обрізає календар                   |
| Скасування за 24 години         | лише для учня; викладач і адмін скасовують будь-коли                              |
| Непідтверджена пошта            | перше бронювання проходить, друге — `EMAIL_NOT_VERIFIED`                          |
| Слот має бути запропонований    | звірка з `availability.getSlots` за той самий день, тариф і локацію               |

**Право на пробне не зберігається прапорцем.** Прапорець довелося б синхронізувати при кожному
скасуванні, і рано чи пізно він розійшовся б із фактами. Запит по заняттях завжди правдивий.

**Перше бронювання працює з непідтвердженою поштою навмисно** — інакше половина заявок помирає
на етапі «перевірте пошту». Але друге вже вимагає робочої адреси, бо саме туди підуть
нагадування.

**Слот перевіряється зверненням до сервісу доступності, а не власним перерахунком.** Так
календар, який бачив відвідувач, і правило, яке застосовує бронювання, — це один і той самий
код. Але вирішує все одно constraint: перевірка лише економить тому, хто програв гонку, зайвий
раунд.

**Позначка результату недоступна, поки заняття не почалося.** Саме вона на етапі 4 списуватиме
заняття з абонемента, тож випадковий клік за день до заняття коштував би учневі списаного
заняття. Наслідок, про який треба знати: продемонструвати `COMPLETED` наскрізно неможливо, не
зрушивши час — під час перевірки `startsAt` заняття було переставлено в минуле запитом до бази.

## 5. Тестування

+32 тести в `booking.router.test.ts`, +2 в `api-client`. Разом по монорепозиторію: 244
(`shared` 64, `api-client` 17, `api` 163).

**Гонка за слот.** Два паралельні `POST /bookings` на одну годину дають рівно один `201` і
один `409` із кодом `SLOT_TAKEN`, і в базі лишається одне заняття.

**І окремий тест на сам constraint** — вставкою просто через Prisma, повз усі перевірки
сервісу. Він потрібен саме тому, що тест на гонку без нього нічого не гарантує: якби
обмеження тихо перестало працювати (втрачене розширення `btree_gist`, переписана міграція),
перевірка в сервісі все одно віддавала б 409 у більшості прогонів, і ми дізналися б про
проблему від двох родин, які прийшли на одну годину. Той самий тест фіксує, що дотик — не
перетин: заняття може починатися рівно тоді, коли попереднє закінчилось.

Під час роботи ця пара себе виправдала одразу: спершу тест на гонку проходив «випадково» —
обидва запити ловила перевірка в сервісі, а справжнє порушення обмеження поверталося як 500,
бо розпізнавання помилки Prisma було неповним. Тест на constraint зробив це видимим.

Інші сценарії, які варто зберегти при рефакторингу: другий запис із непідтвердженою поштою,
скасування пробного й повторний запис на нього, спроба чужого викладача підтвердити заняття,
скасування учнем за 12 годин до початку.

## 6. Веб-інтерфейс

| Сторінка            | Що робить                                                              |
| ------------------- | ---------------------------------------------------------------------- |
| `/teachers`         | публічний список викладачів із напрямами й локаціями                    |
| `/teachers/:id`     | профіль, вибір тарифу, тижневий календар вільного часу, запис           |
| `/cabinet`          | заняття обох сторін: підтвердити, скасувати, позначити результат        |
| `/cabinet/schedule` | робочі правила й відсутності викладача                                  |

**Слот — це два факти, а кнопка несе одне значення.** Кнопка сабміту передає
`startsAt|locationId` одним рядком, який дія розбирає на сервері. Альтернатива — дублювати
сітку в приховані поля — зробила б розмітку вдвічі більшою заради того самого.

**Кожна дія, що змінює стан, — форма, а не посилання.** Підтвердження, скасування й позначка
результату не повинні бути досяжні префетчем або краулером, і працюють без JavaScript.

**Тип заняття вибирається в тій самій формі, а тариф і тиждень — навігацією.** Зміна тарифу
змінює тривалість, а отже й сітку слотів, тож це має бути новий рендер, а не стан у браузері.

**Вибір «пробне» ховається, якщо його вже використано.** Вирішує все одно API; екран лише не
пропонує того, що буде відхилено.

**`proxy.ts` тепер оновлює токен і на публічних сторінках.** Матчер розширено на
`/teachers/:path*`, але редирект на логін лишився тільки для `/cabinet`. Без цього людина з
живою сесією, яка відкрила сторінку запису після перерви, бачила б «увійдіть, щоб записатися»,
будучи авторизованою. Редирект тепер несе `?next=`, тож сесія, що добігла кінця посеред
бронювання, не коштує людині місця в потоці.

## 7. Пастки середовища

- **Значення, експортоване з `'use client'`-модуля, у серверному компоненті не є значенням.**
  Масив назв днів тижня лежав поруч із формою, що ним користується, і в списку правил
  `WEEKDAY_LABELS[rule.weekday]` мовчки давав `undefined` — правила виводились без дня тижня.
  Виявлено в браузері, не тестами. Тепер такі константи живуть у звичайному модулі
  (`lib/studio-time.ts`) з коментарем-попередженням.
- **`GET /me/lessons` повертає заняття з обох боків** — фільтрувати за стороною має той, хто
  питає. Перевірка «чи використано пробне» спершу цього не робила, і викладач, який відкрив
  сторінку колеги, бачив, що його пробне «вже витрачене».
- **Prisma не має власного коду для exclusion constraint.** Порушення приходить як
  `PrismaClientKnownRequestError` з `code: 'P2039'`, а справжній SQLSTATE `23P01` і назва
  обмеження лежать усередині `meta.driverAdapterError.cause`. Розпізнавання шукає і код, і
  назву обмеження — щоб майбутнє exclusion-обмеження на іншій таблиці не сплутали з цим.
- **Наскрізний прогін у Prisma з `Promise.all` пише попередження pg** про паралельні запити на
  одному клієнті. Це попередження, не помилка; у застосунку запити приходять різними
  з'єднаннями з пулу. Тест на гонку прогнано 8 разів поспіль без розбіжностей.

## 8. Свідомо не зроблено

- **Реєстрація й бронювання одним екраном.** Спека описує форму пробного, яка одночасно
  створює акаунт. Зараз неавторизований відвідувач із календаря йде на `/login?next=…` або
  `/register?next=…` і повертається на той самий слот. Потік лишається безперервним, а
  односторінкова версія — це питання конверсії лендінгу, тобто етапу 5, де публічний сайт і
  буде робитися. API підтримує обидва варіанти без змін.
- **Перенесення заняття** як окрема дія. За спекою це `CANCELLED` плюс нова бронь в одній
  транзакції; поки що обидва кроки робляться руками з інтерфейсу. Окрема операція має сенс
  разом з абонементами, коли перенесення не повинне списувати заняття.
- **Абонементні тарифи в записі.** Форма показує лише разові: пакет купують і з нього списують,
  а це `Subscription` з етапу 4. Інакше на разовому записі стояла б ціна восьми занять.
- **Групові заняття** — `format = GROUP` відхиляється з поясненням. Етап 4.
- **Черга сповіщень.** Листи (заявка викладачу, підтвердження учню, скасування іншій стороні)
  йдуть прямим викликом `Mailer`, як і в авторизації, і не валять запит при збої SMTP. Етап 7
  замінить виклик чергою — інтерфейс лишиться.
- **Нагадування за 24 і 2 години** — етап 7, потребує cron.
- **E2E на Playwright.** Спека передбачає рівно два сценарії; обидва зараз покриті
  інтеграційними тестами на рівні API та перевірені в браузері вручну. Автоматизувати їх
  доречно разом із публічним сайтом, коли верстка усталиться.
