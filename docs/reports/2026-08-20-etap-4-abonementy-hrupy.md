**Дата:** 2026-08-20
**Гілка:** `dev`
**Статус:** завершено, критерій етапу виконано
**Спека:** `docs/superpowers/specs/2026-08-13-palitra-talantiv-design.md`, розділ 8

Етап робився інлайново, без окремого плану. Цей документ замінює план.

## 1. Що зроблено

Критерій зі спеки — «викладач веде групу й відмічає відвідуваність» — виконано й перевірено в
браузері наскрізно:

```
викладач → «Мої групи» → група → склад: 2 учні, заявок немає
         → заняття 26 серпня → «Журнал»
         → Коваль Олена: Був · Ткаченко Тарас: Поважна причина → «Зберегти журнал»
         → перезавантаження сторінки: позначки на місці
учениця  → «Групи» → «Гітарний ансамбль» → «Подати заявку»
викладач → склад групи: заявка Коваль Олена → «Прийняти» → вона у складі
```

Окремо перевірено абонемент: учениця обрала на сторінці викладача не тариф, а свій абонемент,
записалась на годину — заняття отримало позначку «З абонемента», а лічильник у кабінеті одразу
став «Лишилось 7 з 8», хоча жодного списання ще не було.

| Вимога етапу              | Стан                                                                        |
| ------------------------- | --------------------------------------------------------------------------- |
| `Subscription`            | ✓ видача адміном за тарифом, оплата, скасування                              |
| Списання                  | ✓ при `COMPLETED`, `NO_SHOW` і пізньому скасуванні                           |
| Резервування              | ✓ заброньовані заняття рахуються проти залишку, з блокуванням рядка          |
| Групи                     | ✓ розклад групи розгортається в реальні заняття                              |
| Заявки на вступ           | ✓ місце тримається від заявки, підтвердження викладачем, `GROUP_FULL`        |
| Відвідуваність            | ✓ журнал на кожне заняття: був / не був / поважна причина                    |

## 2. Модель даних

Дві міграції: `20260820134228_add_subscriptions` і `20260820134251_add_groups_and_attendance`.

| Модель             | Ключові поля                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| `Subscription`     | studentId, teacherId, pricePlanId, lessonsTotal, lessonsUsed, priceUah, validFrom, validTo, paidAt?, status |
| `Group`            | name, teacherId, directionId, locationId, capacity, durationMinutes, isOpenForEnrollment, startsOn, endsOn? |
| `GroupSchedule`    | groupId, weekday, startMinute                                                                       |
| `GroupEnrollment`  | groupId, studentId, status (`PENDING`/`ACTIVE`/`LEFT`), joinedAt, leftAt?                           |
| `LessonAttendance` | lessonId, studentId, status (`PRESENT`/`ABSENT`/`EXCUSED`), markedAt                                |

`Lesson` отримав `groupId`, `subscriptionId` і **nullable `studentId`**.

### Нарешті XOR

Міграція занять з етапу 3 лишила заглушку `lesson_owner_present CHECK ("studentId" IS NOT NULL)`
з коментарем «етап 4 замінить це на XOR». Замінено:

```sql
ALTER TABLE "Lesson" DROP CONSTRAINT lesson_owner_present;

ALTER TABLE "Lesson"
  ADD CONSTRAINT lesson_owner_xor
  CHECK (("studentId" IS NULL) <> ("groupId" IS NULL));
```

Заняття без власника невидиме в обох кабінетах, заняття з двома власниками рахувалося б двічі —
і як індивідуальне, і як зустріч групи.

### Статуси абонемента: тільки два

У спеці `Subscription.status` описаний як поле; у схемі є рівно `ACTIVE` і `CANCELLED`.
«Вичерпаний» і «протермінований» **не зберігаються**: перше виводиться з `lessonsUsed` проти
`lessonsTotal`, друге — з `validTo` проти сьогодні. Збережена копія похідного факту потребує
нічної задачі, щоб лишатися правдою. Це та сама логіка, через яку використане пробне заняття не
стало прапорцем на учні (правило 1 спеки).

### Обмеження, які ловлять помилки коду

```sql
ALTER TABLE "Subscription"
  ADD CONSTRAINT subscription_lessons_range
  CHECK ("lessonsTotal" > 0 AND "lessonsUsed" >= 0 AND "lessonsUsed" <= "lessonsTotal");

ALTER TABLE "GroupEnrollment"
  ADD CONSTRAINT group_enrollment_left_at
  CHECK (("status" = 'LEFT') = ("leftAt" IS NOT NULL));
```

Друга половина першого обмеження — головна: списання це інкремент із коду застосунку, і баг, що
списує двічі, тихо з'їв би оплачене заняття. Тепер він падає голосно. Обмеження на
`GroupEnrollment` не дає зберегти напівзастосовану зміну: «пішов, але без дати» або «активний,
але з датою виходу».

## 3. Абонемент: резервує при бронюванні, списує при закритті

Правило 6 спеки: бронювання **не списує**, але **резервує** — забронювати можна, поки
`lessonsUsed + (PENDING і CONFIRMED занять абонемента) < lessonsTotal`. Без цієї умови учень із
абонементом на 8 занять забронював би 20, бо списання відбувається постфактум.

Перевірка й вставка живуть в одній транзакції, і перший запит у ній — блокування рядка:

```sql
SELECT ... FROM "Subscription" WHERE "id" = $1 FOR UPDATE
```

Дві вкладки, що бронюють останнє заняття пакета, обидві читають «лишилось одне» й обидві пишуть.
`FOR UPDATE` змушує другу чекати, тож кількість, яку вона прочитає, вже правдива. Це той самий
хід думки, що й exclusion constraint на календарі, застосований до грошей.

Списання — одним запитом, а не «прочитати, додати, записати»:

```sql
UPDATE "Subscription"
SET "lessonsUsed" = "lessonsUsed" + 1, "updatedAt" = now()
WHERE "id" = $1 AND "lessonsUsed" < "lessonsTotal"
```

Умова в `WHERE` — те, що не дає списати дев'яте заняття з восьми; `subscription_lessons_range` —
страховка під нею. Позначка результату теж робиться з фільтром по статусу
(`updateMany where { id, status: 'CONFIRMED' }`), тож два кліки, що прийшли разом, не спишуть
заняття двічі.

### Пізнє скасування коштує заняття — і кнопка «без списання»

Правило 4 спеки: скасувати самому можна не пізніше ніж за 24 години, пізніше — тільки через
викладача, і заняття списується. Реалізовано буквально: скасування всередині останньої доби
списує заняття з абонемента.

Але з цього правила є випадок, якого воно не розрізняє: заняття скасовує сам викладач, бо
захворів. Тому в API з'явився `waiveCharge`, а на картці заняття — друга кнопка «Скасувати без
списання», яку бачить лише викладач і лише коли до заняття менше доби. Судження лишається там,
куди його кладе спека — у викладача, — а типова поведінка лишається правилом.

## 4. Групи: розклад — це намір, заняття — це рядки

`GroupSchedule` каже «щовівторка о 17:00». Це намір, а не календар: щоб групове заняття займало
викладачеві час і мало куди чіпляти відвідуваність, потрібні реальні рядки в `Lesson`. Їх
створює `computeGroupLessons` — друга чиста функція проєкту після `computeFreeSlots`: жодної
бази, жодного годинника, все приходить аргументами.

Її поведінка, зафіксована 13 табличними тестами:

- локальна година тримається через переходи часу: група, що збирається о 17:00, збирається о
  17:00 і 20 жовтня (14:00 UTC), і 27-го (15:00 UTC);
- зустріч, що потрапляє в неіснуючу годину весняного переходу, **пропускається**, а не тихо
  переїжджає на іншу хвилину;
- генерація починається з пізнішої з двох дат — початку курсу або сьогодні, — тож зустріч, що
  вже відбулася сьогодні, не створюється вдруге;
- курс без `endsOn` генерується на 8 тижнів уперед (`GROUPS.generationHorizonDays`).

### Чому генерація навмисно не в транзакції

Зустріч групи може накластися на індивідуальне заняття, яке викладач уже має. У Postgres
порушення обмеження скасовує всю транзакцію — один невдалий вівторок забрав би з собою решту
п'ятнадцять. Тому колізії шукаються читанням наперед, решта вставляється по одній, а
`lesson_no_overlap` лишається страховкою на випадок броні, що прилетіла між читанням і вставкою.

Пропущені зустрічі не зникають мовчки: `POST /groups` повертає `skippedOccurrences`, і форма
пише «Групу збережено, але цей час уже зайнятий і заняття не створено: 2 вересня, 17:00».
Розклад із дірою, про яку ніхто не сказав, гірший за розклад із поясненням.

**Зміна розкладу перегенеровує тільки майбутнє.** Минулі зустрічі лишаються разом зі своїми
журналами. Перевірено тестом: група перевелася з 11:00 на 12:00 у середині вересня — 2 і 9
вересня лишились об одинадцятій, 23 і 30 стали о дванадцятій.

### Місце тримається від заявки

Правило 8 спеки. `capacity` рахує `PENDING + ACTIVE` разом, інакше викладач підтвердив би дев'ять
заявок на вісім стільців і комусь довелося б сказати «йдіть додому». Один рядок на людину на
групу назавжди: хто пішов і повернувся, переписує свій рядок, а унікальний індекс на пару робить
другу заявку неможливою.

### Вид групового заняття

`kind` у групового заняття — `SINGLE`. Це навмисно: за спекою `kind` відповідає на питання «чим
заняття оплачене», а `groupId` — на питання «чиє воно». Додавати `GROUP` у `kind` означало б
кодувати одне й те саме двома полями, які можуть розійтися. Статус — `CONFIRMED`, бо зустріч
групи не заявка, що чекає відповіді викладача, а розклад, який він сам і склав.

## 6. Тестування

+40 тестів в `api` (13 на `computeGroupLessons`, 19 на абонементи, 21 на групи — з двох файлів
модуля груп 34), +20 у `shared`, +6 в `api-client`. Разом по монорепозиторію: **323**
(`shared` 84, `api-client` 23, `api` 216).

**Тест на блокування рядка перевірено на здатність падати.** Два паралельні бронювання на різні
години з пакета, у якому лишилось одне заняття, дають `201` і `409 SUBSCRIPTION_EXHAUSTED`.
Прибрано `FOR UPDATE` з запиту — тест одразу став `[201, 201]`. Повернуто. Без такої перевірки
тест на гонку нічого не гарантує: на етапі 3 схожий тест певний час проходив «випадково».

Інші сценарії, які варто зберегти при рефакторингу: списання при `NO_SHOW`, скасування за
добу до заняття (не списує) і за 12 годин (списує), `waiveCharge`, подвійне закриття заняття,
пакет чужого учня, пакет іншого викладача, дата поза дією пакета, `GROUP_FULL` через
непідтверджені заявки, повторна заявка після виходу, позначка для того, хто не в групі.

## 7. Веб-інтерфейс

| Сторінка                              | Що робить                                                    |
| ------------------------------------- | ------------------------------------------------------------ |
| `/groups`, `/groups/:id`              | публічний перелік груп і заявка на вступ                      |
| `/cabinet`                            | + панелі «Абонементи» і «Групи»                               |
| `/cabinet/groups`                     | групи викладача та форма створення                            |
| `/cabinet/groups/:id`                 | заявки, склад, перелік занять                                 |
| `/cabinet/lessons/:id/attendance`     | журнал відвідуваності                                         |

**Тариф і абонемент — один список.** На сторінці викладача пакет стоїть поруч із разовим
тарифом: з погляду календаря це та сама відповідь на те саме питання — чим оплачене заняття і
скільки воно триває. Розділяти їх на два потоки означало б два способи натиснути одну кнопку.
Коли обрано пакет, вибір «пробне / разове» зникає: пакет уже все вирішив.

**Журнал — радіо-рядок на дитину, а не список галочок.** Викладач проходить групу з восьми за
один прохід, і випадний список коштував би два дотики на ім'я. «Не відмічено» — повноцінна
відповідь: журнал зберігається цілком, тож зняти помилкову позначку можна, і збереження не
лишає торішньої відповіді.

**Форма розкладу групи — три фіксовані рядки.** Кнопка «додати ще» без JavaScript нічого не
означає, а курсів, що збираються частіше трьох разів на тиждень, у студії немає. Рядок без часу
— рядок, який викладач лишив порожнім.

**`describeError` тепер знає всі доменні коди.** До цього етапу мапа покривала лише коди
авторизації, і «Цей час щойно зайняли» показувалось як «Не вдалося виконати дію. Спробуйте ще
раз за хвилину». Прогалину видно було одразу, щойно з'явилися `GROUP_FULL` і
`SUBSCRIPTION_EXHAUSTED`.

## 8. Пастки середовища

- **Попередження pg про паралельні запити на одному клієнті — не наш баг.** Воно виникає, коли
  Prisma відповідає на запис із `include`: під капотом це неявна транзакція, і під-запити
  зв'язків летять на одне з'єднання паралельно. Відтворюється одним `update` з трьома `include`
  без жодної нашої транзакції; існувало ще на етапі 3 у `confirm`. Наслідок для коду: усередині
  явних транзакцій `include` не використовується — читання для відповіді робиться після коміту,
  що заодно скорочує час утримання блокування `FOR UPDATE`.
- **`as const` на об'єкті `include` робить вкладені масиви `readonly`,** а Prisma чекає
  змінюваних. Замість `[...OCCUPYING]` усередині літерала константи оголошені з явним типом
  (`GroupEnrollmentStatus[]`), а сортування розкладу з семи рядків перенесене в JS.
- **`capacity` мінімум 2 — і в zod, і в базі.** Перший варіант тесту створював групу на одне
  місце, щоб швидше довести її до заповнення; вона просто не створилась. Група з однієї людини —
  це індивідуальне заняття.
- **Автозаповнення браузера підміняє поля форми.** При перевірці в браузері `form_input`
  спрацював, а Chrome підставив збережені `admin`/пароль поверх. Для повторюваних прогонів
  надійніше очищати поле й друкувати текст.

## 9. Свідомо не зроблено

- **Оплата групового курсу.** `Subscription` — це пакет індивідуальних занять з одним
  викладачем; групу оплачують як курс. Тарифи `format = GROUP` у сіді вже є, але списання за
  відвідуваність до них не прив'язане: критерій етапу — «веде групу й відмічає відвідуваність»,
  а не «продає курс». Зв'язок «журнал → гроші» вимагає окремої моделі оплати курсу і має сенс
  разом з адмінкою (етап 6).
- **Учень не бачить власних позначок.** Журнал читає лише викладач заняття. Показати учневі його
  відвідуваність — питання ще одного прочитання тієї самої таблиці; додаватиметься, коли з'явиться
  екран прогресу.
- **Продовження занять групи щотижневим cron.** Курс без `endsOn` генерується на 8 тижнів;
  спека передбачає, що далі його продовжує cron. Планувальник з'являється на етапі 7 разом із
  нагадуваннями, і продовження стане ще одним його завданням.
- **Перенесення заняття** без списання з абонемента — тепер для цього є все, крім самої
  операції: `CANCELLED` з `waiveCharge` плюс нова бронь. Окрема транзакційна дія лишається на
  потім.
- **Сповіщення про заявку до групи й про її підтвердження.** Індивідуальні заняття листи
  надсилають; група поки ні — дописувати другий прямий виклик `Mailer` за два етапи до черги
  сповіщень не варто. Скасування групової зустрічі з тієї ж причини нікого не повідомляє.
- **Адмінський екран видачі абонементів.** Ендпоінти є й закриті `requireRole('ADMIN')`;
  екран для них — етап 6, де адмінка робиться цілком.
- **E2E на Playwright** — як і на етапі 3, обидва сценарії спеки покриті інтеграційними тестами
  й перевірені в браузері вручну.
