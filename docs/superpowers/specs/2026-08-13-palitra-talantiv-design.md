# Палітра талантів — дизайн системи

**Дата:** 2026-08-13
**Статус:** затверджено, готове до планування етапу 0

## 1. Контекст

Вокальна студія «Палітра талантів» працює в Черкасах із 2011 року при Міському будинку культури
ім. Івана Кулика. Напрями: вокал, фортепіано, гітара, укулеле. Індивідуальні та групові заняття для
дітей і дорослих (4–45 років). Дві локації: вул. Благовісна, 170 і бул. Шевченка, 276. Викладачів
7–8. Студія бере участь у конкурсах, зокрема міжнародних, і проводить концерти та відкриті уроки.

Зараз запис і комунікація йдуть через Instagram і телефон.

### Що будуємо

Сайт-презентацію студії плюс систему запису на заняття з кабінетами для викладачів і учнів.
Пізніше — мобільний застосунок на React Native як другий клієнт того самого API.

### Чого не будуємо

- Онлайн-оплату. Гроші приймаються поза системою, адмін лише проставляє «оплачено».
- Мобільний застосунок у цьому циклі. Готуємо ґрунт, реалізуємо окремо.
- WebGL/three.js візуалізації. Опціонально після MVP.
- Окрему роль «батьки». Контакт дорослого зберігається в профілі учня.

### Хостинг

Рішення відкладене до етапу 8. Система проектується портативною: усі налаштування через змінні
оточення, `Dockerfile` для API, жодних платформенних SDK у бізнес-логіці.

Розглянуті варіанти:

- **Vercel (веб) + Railway (API + Postgres)** — ~$5–10/міс, Express як постійний процес, будь-який cron.
- **Vercel + Supabase** — безкоштовно на старті, але free-тариф Supabase засинає після 7 днів без
  запитів, а Express усе одно треба десь запускати (Edge Functions — це Deno, не Node).
- **Свій VPS** — дешевше вдовгу, дорожче в обслуговуванні.

Якщо береться Supabase: рядок з'єднання через pooler (порт 6543) для застосунку і прямий (5432) для
міграцій, інакше `prisma migrate` ламається.

## 3. Структура проєкту

```
palitra-talantiv-che/
├─ apps/
│  ├─ web/                 Next.js — публічний сайт + кабінети
│  └─ api/                 Express + TypeScript
├─ packages/
│  ├─ shared/              zod-схеми домену, виведені типи, коди помилок
│  ├─ api-client/          типізований клієнт поверх fetch
│  └─ config/              tsconfig / eslint / prettier
├─ docker-compose.yml      postgres + mailhog
├─ turbo.json
└─ pnpm-workspace.yaml
```

`packages/shared` — єдине джерело правди. Кожна сутність описується zod-схемою один раз: Express
валідує нею запити, Next бере ті самі схеми у форми через `zodResolver`, типи виводяться через
`z.infer`. `apps/mobile` підключить цей самий пакет без дублювання типів.

### Модулі `apps/api`

```
src/
  modules/
    auth/           реєстрація, логін, ротація токенів
    users/          профілі, ролі
    teachers/       профілі викладачів, локації
    availability/   правила розкладу, винятки, обчислення вільних слотів
    booking/        створення / підтвердження / скасування занять
    subscriptions/  абонементи, списання занять
    groups/         групи, склад, заявки, відвідуваність
    events/         концерти, відкриті уроки, конкурси
    content/        напрями, ціни, галерея, відгуки, досягнення
    notifications/  черга сповіщень і канали доставки
  lib/              prisma, StorageAdapter, mailer, DomainError
  http/             app.ts, middleware: auth, rbac, validate, errorHandler
```

Три шари в кожному модулі: **роутер** (HTTP, валідація, коди відповідей) → **сервіс** (бізнес-правила,
транзакції) → **Prisma**. Роутер не знає про Prisma, сервіс не знає про `req`/`res`. Завдяки цьому
сервіси викликаються з cron-задач і тестів напряму.

### Ключове архітектурне рішення

Найскладніша логіка проєкту — «які слоти вільні у викладача X» — виноситься в чисту функцію без
доступу до БД:

```ts
computeFreeSlots({
  rules,           // AvailabilityRule[]
  exceptions,      // AvailabilityException[]
  busyLessons,     // Lesson[] зі статусами PENDING | CONFIRMED
  range,           // { from, to }
  durationMinutes, // 30 | 45 | 60
  stepMinutes,     // крок сітки, константа конфігу — 15
}): Slot[]
```

Усе, що вона знає — масиви на вході. Ніякого Prisma, ніякого `new Date()` всередині. Уся календарна
арифметика — переходи на літній час, накладання відпусток, часткові перетини — покривається
табличними юніт-тестами без бази й моків. Це та частина, де баги найдорожчі й найтихіші.

## 4. Модель даних

### Час

Усе зберігається в `timestamptz` в UTC. Часовий пояс студії — константа `Europe/Kyiv`.
`AvailabilityRule` зберігає **локальний** час доби плюс день тижня; розгортання в конкретні дати
відбувається в київському поясі.

Це навмисно: у ніч переходу на літній час «щовівторка о 17:00» — різні моменти в UTC до і після
переходу. Зберігання правил в UTC зсувало б розклад на годину двічі на рік.

### Користувачі та ролі

| Модель             | Ключові поля                                                                                                               |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `User`             | email, passwordHash, role (`ADMIN`/`TEACHER`/`STUDENT`), firstName, lastName, phone, avatarUrl, emailVerifiedAt, createdAt |
| `RefreshToken`     | userId, tokenHash, expiresAt, revokedAt, userAgent                                                                         |
| `TeacherProfile`   | userId (1:1), bio, experienceYears, photoUrl, isPublished, sortOrder                                                       |
| `StudentProfile`   | userId (1:1), birthDate, guardianName, guardianPhone, adminNotes                                                           |
| `Location`         | name, address, mapUrl                                                                                                      |
| `TeacherLocation`  | teacherId, locationId (M:N)                                                                                                |
| `TeacherDirection` | teacherId, directionId (M:N)                                                                                               |

Роль — поле в `User`, а не окрема таблиця: ролей три й вони фіксовані, повноцінна RBAC була б
оверінжинірингом. `guardianName`/`guardianPhone` закривають дітей від 4 років без окремої ролі.

Що викладач викладає, задається зв'язком `TeacherDirection` із довідником `Direction`, а не окремим
полем-переліком. Інакше «вокал» існував би у двох місцях — в enum профілю та в довіднику напрямів —
і фільтр «покажи всіх, хто веде гітару» довелося б писати двічі.

### Доступність викладача

| Модель                  | Ключові поля                                                                  |
| ----------------------- | ----------------------------------------------------------------------------- |
| `AvailabilityRule`      | teacherId, locationId, weekday (0–6), startTime, endTime, validFrom, validTo? |
| `AvailabilityException` | teacherId, startsAt, endsAt, kind (`VACATION`/`SICK`/`BLOCKED`), note         |

`validFrom`/`validTo` дозволяють змінити графік із дати без втрати історії. Винятки — діапазони
дат-часу, а не позначки на днях, бо відпустка може починатись з середини дня.

### Заняття, абонементи, групи

| Модель             | Ключові поля                                                                                                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Lesson`           | teacherId, **studentId?**, **groupId?**, locationId, startsAt, endsAt, durationMinutes, kind (`TRIAL`/`SINGLE`/`SUBSCRIPTION`), status, subscriptionId?, cancelledById?, cancelReason? |
| `Subscription`     | studentId, teacherId, lessonsTotal, lessonsUsed, priceUah, validFrom, validTo, paidAt?, status                                                                                         |
| `Group`            | name, teacherId, directionId, locationId, capacity, durationMinutes, isOpenForEnrollment, startsOn, endsOn?                                                                            |
| `GroupSchedule`    | groupId, weekday, startTime                                                                                                                                                            |
| `GroupEnrollment`  | groupId, studentId, status (`PENDING`/`ACTIVE`/`LEFT`), joinedAt, leftAt?                                                                                                              |
| `LessonAttendance` | lessonId, studentId, status (`PRESENT`/`ABSENT`/`EXCUSED`)                                                                                                                             |

Статуси заняття: `PENDING` → `CONFIRMED` → `COMPLETED` / `CANCELLED` / `NO_SHOW`.

**`Lesson` — одна таблиця для всіх типів занять.** Пробне, разове й абонементне відрізняються полем
`kind`, індивідуальне від групового — заповненим `studentId` або `groupId`. Окремі таблиці
перетворювали б кожен перегляд календаря на UNION з кількох джерел і робили б перевірку перетинів
ненадійною.

**Рівно одне з `studentId` / `groupId`:**

```sql
ALTER TABLE "Lesson" ADD CONSTRAINT lesson_owner_xor
  CHECK (("studentId" IS NULL) <> ("groupId" IS NULL));
```

**Захист від подвійного бронювання — на рівні БД, не коду:**

```sql
ALTER TABLE "Lesson" ADD CONSTRAINT lesson_no_overlap
  EXCLUDE USING gist (
    "teacherId" WITH =,
    tstzrange("startsAt", "endsAt") WITH &&
  ) WHERE (status IN ('PENDING', 'CONFIRMED'));
```

Перевірка «чи вільний слот» у застосунку завжди має вікно гонки: двоє батьків тиснуть «Записатись»
на той самий слот в одну секунду, обидва читають «вільно», обидва пишуть. Constraint робить друге
бронювання фізично неможливим — сервіс ловить помилку й повертає `409`. Побічна вигода від єдиної
таблиці: групове заняття автоматично блокує викладачеві індивідуальні слоти на той самий час і
навпаки.

Prisma не вміє exclusion constraints декларативно — це окрема SQL-міграція. Потрібне розширення
`btree_gist`.

`endsAt` зберігається поряд із `durationMinutes` навмисно, хоч і виводиться з нього. Exclusion
constraint працює з `tstzrange("startsAt", "endsAt")`, а обчислюване в запиті значення індекс не
покриє. Узгодженість двох полів забезпечується тим, що `endsAt` виставляється виключно в сервісі
бронювання — прямих записів у `Lesson` повз сервіс немає.

**Заняття групи створюються наперед.** `GroupSchedule` — це намір, а не розклад: щоб групове заняття
блокувало викладачеві слоти й мало куди чіпляти відвідуваність, потрібні реальні рядки в `Lesson`.
При створенні або зміні графіка групи сервіс генерує заняття на весь період `startsOn..endsOn`
(якщо `endsOn` не задано — на 8 тижнів уперед, далі щотижневий cron продовжує). Зміна `GroupSchedule`
перегенеровує тільки майбутні заняття, минулі лишаються недоторканими разом із відвідуваністю.

## 5. Бізнес-правила

1. **Пробне заняття** — одне безкоштовне на учня назавжди, не на кожного викладача. Факт
   використання не зберігається окремим прапорцем, а виводиться запитом: чи є в учня `Lesson` із
   `kind = TRIAL` і статусом, відмінним від `CANCELLED`. Скасоване пробне повертає право на нове —
   інакше випадкове скасування назавжди позбавляє людину безкоштовного заняття.
2. **Тривалість** — 30 / 45 / 60 хвилин, приходить із `PricePlan`, а не з вибору учня.
3. **Крок сітки слотів** — 15 хвилин, константа конфігу.
4. **Вікно скасування** — учень скасовує не пізніше ніж за 24 години до початку. Пізніше — тільки
   через викладача, заняття списується з абонемента.
5. **Горизонт бронювання** — 4 тижні вперед.
6. **Списання з абонемента** — при переході в `COMPLETED`. `NO_SHOW` теж списує. Бронювання не
   списує, але **резервує**: забронювати можна, поки
   `lessonsUsed + (кількість PENDING і CONFIRMED занять абонемента) < lessonsTotal`. Без цієї умови
   учень із абонементом на 8 занять забронював би 20 — списання ж відбувається лише постфактум.
   Вичерпаний абонемент → `SUBSCRIPTION_EXHAUSTED`.
7. **Слот не резервується** під час вибору. Резервування вимагало б таблиці блокувань із TTL і
   фонового прибирання — складність, що не окупається на потоці студії з 8 викладачами.
8. **Запис у групу** — учень подає заявку (`GroupEnrollment.PENDING`), викладач або адмін
   підтверджує. Місце тримається на час розгляду й рахується проти `capacity`.

## 6. Потоки

### Реєстрація на пробне заняття

Форма бронювання пробного **одночасно створює акаунт**: один екран — ім'я, телефон, email, пароль,
вибір викладача й слота.

Без акаунта учень не може подивитись, скасувати чи перенести заняття, і будь-яка зміна знову йде
через телефон — тобто система не розвантажує студію, а лише додає їй ще один канал.

Email підтверджується листом, але **перше бронювання працює одразу**. Непідтверджений email блокує
лише повторні бронювання — інакше половина заявок помирає на етапі «перевірте пошту».

### Бронювання слота

```
учень обирає викладача
  → обирає напрям і тариф (фіксує тривалість)
  → бачить календар на 4 тижні:
      вільні слоти = робочі правила − винятки − зайняте
  → тисне слот
  → POST /bookings, у транзакції:
      перевірка правил (пробне вже було? абонемент активний? слот у горизонті?)
      + INSERT Lesson (PENDING)
      + exclusion constraint ловить гонку → 409 SLOT_TAKEN
  → сповіщення викладачу (in-app + email)
  → викладач підтверджує → CONFIRMED → сповіщення учню
```

### Скасування та перенесення

Перенесення — не окрема операція, а `CANCELLED` плюс нове бронювання в одній транзакції. Одна
сутність замість двох, історія лишається повною.

Правило 24 годин застосовується **в сервісі**, не на фронті. Кнопка ховається, але сервер перевіряє
незалежно — інакше правило обходиться через API, а для мобілки це єдиний захист.

### Кабінет викладача

Свій тиждень у календарі (індивідуальні та групові разом), підтвердження заявок, редагування робочих
правил, відпустки, свої групи — склад, заявки на вступ, відвідуваність. Позначка `COMPLETED` /
`NO_SHOW` після заняття: саме вона списує абонемент, тому екран має бути коротким.

### Кабінет адміна

Викладачі (створення акаунтів, публікація профілів), увесь розклад, усі групи, абонементи й позначки
«оплачено», події студії, контент сайту.

### Матриця прав

| Дія                                  |     Учень      |       Викладач       |     Адмін     |
| ------------------------------------ | :------------: | :------------------: | :-----------: |
| Бачити вільні слоти                  |       ✓        |          ✓           |       ✓       |
| Бронювати собі                       |       ✓        |          —           | ✓ (будь-кому) |
| Підтверджувати заняття               |       —        |         свої         |       ✓       |
| Скасувати                            | своє, >24 год  |         свої         |       ✓       |
| Правила розкладу й відпустки         |       —        |         свої         |       ✓       |
| Групи: склад, заявки, відвідуваність |     заявка     |         свої         |       ✓       |
| Абонементи, позначка «оплачено»      | перегляд свого | перегляд своїх учнів |       ✓       |
| Контент сайту й події                |       —        |          —           |       ✓       |

Реалізація: middleware `requireRole(...)` для грубої перевірки **плюс** перевірка володіння в сервісі
(`lesson.teacherId === user.id`). Друге критичніше: без нього викладач A підтверджує заняття
викладача B, підставивши чужий id.

### Сповіщення

Подія домену → запис у `Notification` → доставка каналами. У MVP `IN_APP` і `EMAIL`.

Нагадування — cron раз на годину: знайти `CONFIRMED` заняття, що починаються через 24 год і через
2 год, і в яких ще немає доставки такого типу. Ідемпотентність через унікальний ключ
`(lessonId, type)` — інакше при перезапуску процесу учні отримають дублі.

### Помилки

Один клас `DomainError` з кодом → централізований `errorHandler` мапить у HTTP-статус і стабільний
JSON `{ code, message, details? }`.

Коди: `SLOT_TAKEN` (409), `TRIAL_ALREADY_USED` (409), `TOO_LATE_TO_CANCEL` (422),
`SUBSCRIPTION_EXHAUSTED` (409), `GROUP_FULL` (409), `OUTSIDE_BOOKING_HORIZON` (422),
`NOT_TEACHER_OWNED` (403).

Коди живуть у `packages/shared`, тому фронт і мобілка показують тексти за кодом, а не парсять рядки.

### Брендинг

Стилістика зчитана з Instagram-профілю студії. Тема сайту — **світла й тепла**: кремове тло, а не
біле й не темне. Це узгоджується і з постовими шаблонами, і з реальним інтер'єром студії (світле
дерево, кремові стіни, фіолетова неонова вивіска).

Графічна мова побудована на самій назві: фіолетові, помаранчеві й зелені мазки пензлем на кремовому,
дрібні дудли — зірочки, сердечка, нотний стан. Лого існує у двох версіях: суворій («PALITRA»
капітеллю з розрідженим «TALANTIV») і теплій рукописній («Palitra talantiv, музична студія»).

| Токен             | Приблизне значення | Призначення                                   |
| ----------------- | ------------------ | --------------------------------------------- |
| `--color-primary` | `#7B4FC9`          | Фіолетовий: текст, кнопки, акценти            |
| `--color-accent`  | `#F08A2C`          | Помаранчевий: заклики до дії, плями-заголовки |
| `--color-support` | `#93C83E`          | Зелений: декор, ілюстративні мазки            |
| `--color-bg`      | `#F7F3EA`          | Кремове тло                                   |
| `--color-ink`     | `#1C1B22`          | Основний текст                                |

Значення зняті з JPEG-скріншота й підлягають уточненню за оригіналами логотипу.

**Обмеження за контрастом — обов'язкові, не рекомендаційні:**

- Фіолетовий на кремовому — 5.0:1, на білому — 5.5:1. Проходить WCAG AA для звичайного тексту.
- Помаранчевий на кремовому — 2.3:1, **для тексту не використовується**. CTA робиться помаранчевою
  плашкою з майже чорним текстом (8.4:1), а не помаранчевим написом на тлі.
- Зелений на кремовому — 1.8:1, **виключно декор**.

Інстаграмні шаблони не переносяться на сайт один-в-один саме через це: у стрічці помаранчевий
заголовок на кремовому читається, бо він великий і дивляться з телефона впритул, а на сайті це буде
основний текст, який частина відвідувачів не прочитає.

**Потрібно від студії:** оригінали логотипу у векторі (обидві версії), назви фірмових шрифтів,
елементи-мазки та дудли окремими файлами.

**Процес роботи над фронтендом.** Уся візуальна робота ведеться через skill `frontend-design`. Це
стосується етапу 5 (публічний сайт) і етапу 6 (адмінка) повною мірою, а на етапі 0 — шару
дизайн-токенів, який закладається одразу, щоб решта будувалась на ньому, а не поверх нього.

**Структура хайлайтів профілю підтверджує розділи сайту:** Викладачі, Наш прайс, Як нас знайти,
Конкурси, Наші учні, Правила студії, Групи та дорослі. «Правила студії» варто винести окремою
сторінкою — на них посилатиметься форма бронювання.

Брендинг не блокує етапи 0–4.

## 9. Тестування

**Юніт (Vitest).** Головний фокус — `computeFreeSlots`. Функція чиста, тому тести табличні й дешеві.
Обов'язкові випадки: перехід на літній і зимовий час, відпустка накриває частину робочого дня, два
суміжні заняття без зазору, різні тривалості на одній сітці, правило з `validTo` в минулому. Сюди ж
правило 24 годин і списання абонемента.

**Інтеграційні (Vitest + supertest + справжній Postgres у Docker).** Мокати базу тут безглуздо:
половина логіки — це саме обмеження бази. Ключовий тест — **гонка за слот**: два паралельні
`POST /bookings` на один слот дають рівно один `201` і один `409`. Без нього exclusion constraint
може мовчки не працювати, і ми дізнаємось про це від батьків, які прийшли вдвох на одну годину. Плюс
перевірка прав: викладач A звертається до ресурсів викладача B → `403`.

**E2E (Playwright) — рівно два сценарії:** «новий учень бронює пробне» і «викладач підтверджує та
позначає проведеним». Поломка будь-якого з них означає, що продукт не працює. Більше E2E не пишемо —
вони дорогі в підтримці й ламаються від верстки.

**Не тестуємо:** обгортки над Prisma, презентаційні компоненти, гетери.

**Seed з реалістичними даними** — 8 викладачів, 2 локації, робочі графіки, кілька учнів, дві групи,
минулі й майбутні заняття. Без нього неможливо ані клікати інтерфейс, ані відтворювати баги.

**CI на кожен PR:** lint, typecheck, юніт, інтеграційні.
