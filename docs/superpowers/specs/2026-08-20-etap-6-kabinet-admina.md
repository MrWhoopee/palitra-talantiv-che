# Етап 6: кабінет адміна

**Дата:** 2026-08-20
**Статус:** затверджено, реалізація почата
**Базова спека:** [Дизайн системи](2026-08-13-palitra-talantiv-design.md), розділ 8, рядок «6. Адмінка»

## 1. Межі

Базова спека описує адмінку двічі й по-різному: рядок таблиці етапів обіцяє «керування
викладачами, контент-моделі, події, `StorageAdapter`», а розділ «Кабінет адміна» — те саме плюс
увесь розклад, усі групи й абонементи. Береться ширший варіант: повний кабінет.

**Входить:**

- запрошення й профілі викладачів;
- довідники: локації, напрями, прайс;
- контент сайту: події, галерея, відгуки, досягнення;
- тексти сторінок і контакти студії;
- завантаження зображень (`StorageAdapter`);
- операційка: весь розклад студії, усі групи із заявками, абонементи з позначкою «оплачено»,
  список учнів, бронювання за учня.

**Не входить:**

- журнал дій адміна — жодна вимога його не просить, а таблиця, яку ніхто не читає, все одно
  наповнюється;
- драйвер S3 — етап 8, коли буде обрана платформа;
- WYSIWYG і конструктор сторінок — сторінок сім і вони не міняються;
- перетягування мишею для порядку сортування;
- мультимовність — виключена базовою спекою.

## 2. Модель даних

Чотири зміни, усі адитивні: жодна не переписує наявних рядків.

### `OneTimeTokenKind` отримує `INVITE`

Таблиця одноразових токенів з етапу 1 уже вміє все потрібне: хеш замість самого секрета, термін
дії, одноразовість, прив'язка до користувача. Поле `kind` існує рівно для цього випадку — щоб
лист-запрошення не можна було відкупорити як скидання пароля.

### `User.passwordHash` стає `String?`

Запрошений викладач має акаунт до того, як має пароль.

Це найризикованіша правка етапу. Кожен шлях входу мусить трактувати `null` як «увійти
неможливо», інакше порожній пароль зійде за збіг. Перевірка на `null` ставиться **до** виклику
`bcrypt.compare`, а не покладається на його поведінку, і закривається окремим тестом.

### `SiteText`

| Поле        | Тип        | Призначення                            |
| ----------- | ---------- | -------------------------------------- |
| `key`       | `String` @id | `about`, `rules`, …                  |
| `title`     | `String`   | заголовок сторінки                     |
| `body`      | `String`   | markdown                               |
| `updatedAt` | `DateTime` |                                        |

Не довільні сторінки: набір ключів зафіксований у коді, адмінка редагує наявні й не створює
нових. Сторінка без рядка в базі показує текст із коду — на порожній таблиці сайт не ламається.

### `SiteSetting`

`key` → `value`. Телефон, інстаграм, інші соцмережі, години роботи. `apps/web/src/lib/studio.ts`
лишається значенням за замовчуванням, рядки з бази накриваються поверх нього. Читання —
з кешуванням на рівні `fetch`, інакше футер коштував би запиту на кожен рендер сторінки.

### `TeacherProfile.isActive`

`Boolean @default(true)`. Викладача, який пішов, видалити неможливо: на нього посилаються
проведені заняття, а переписувати історію не можна. `isPublished` прибирає його з сайту,
`isActive` — з випадайок при бронюванні й із побудови вільних слотів.

### Чого немає

Окремої таблиці для завантажених файлів. Посилання лежить у тому ж полі, що й зараз (`coverUrl`,
`photoUrl`, `url`, `imageUrl`). Ціна рішення — файл, відв'язаний від запису при заміні картинки,
лишається на диску. Свідомо: збирач сміття тут коштує дорожче за кілька мегабайтів.

## 3. Поверхня API

### Розділення роутерів

Логіка лишається в сервісі свого модуля — там, де вже лежать читання тих самих таблиць. Маршрути
діляться на файл по аудиторії:

```
content.router.ts   → content.public.router.ts  + content.admin.router.ts
teachers.router.ts  → teachers.public.router.ts + teachers.admin.router.ts
                    + admin.router.ts  — монтує адмінські роутери під /admin
```

`admin.router.ts` вішає `requireRole('ADMIN')` **один раз на префікс**. Це головна причина
такого розділення: забути охоронця на окремому маршруті стає неможливо, а розсипаний по тридцятьох
маршрутах `requireRole` рано чи пізно десь пропущено, і цього не видно на очі.

Публічні роутери лишаються такими, як були, разом із обіцянкою в коментарі `content.router.ts`
(«public and read-only, all of it»).

### Маршрути

| Група      | Маршрути                                                                                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Викладачі  | `GET/POST /admin/teachers`, `PATCH /admin/teachers/:id`, `PUT …/directions`, `PUT …/locations`, `POST …/reinvite`                                                  |
| Довідники  | `GET/POST/PATCH/DELETE` для `/admin/locations`, `/admin/directions`, `/admin/price-plans`                                                                          |
| Контент    | те саме для `/admin/events`, `/admin/gallery`, `/admin/testimonials`, `/admin/achievements`                                                                        |
| Тексти     | `GET /admin/site-texts`, `PUT /admin/site-texts/:key`, `GET/PUT /admin/settings`                                                                                   |
| Операційка | `GET /admin/lessons?from&to&teacherId&status`, `POST /admin/lessons`, `GET /admin/subscriptions`, `GET /admin/groups`, `GET /admin/students?q`, `GET /admin/enrollments?status` |
| Файли      | `POST /admin/uploads`                                                                                                                                             |
| Публічне   | `POST /auth/accept-invite` — єдиний новий маршрут поза `/admin`                                                                                                    |

Адмінські `GET` віддають і чернетки теж — саме цим вони відрізняються від публічних однойменних.

Схеми входу — у `packages/shared`, поруч із наявними: форма й API валідуються одним і тим самим
об'єктом, тож правило не може розійтися між ними.

Нових кодів помилок не потрібно: `INVALID_TOKEN` покриває прострочене запрошення, `EMAIL_TAKEN` —
повторне, `NOT_FOUND` і `FORBIDDEN` — решту.

## 4. Завантаження зображень

```ts
interface StorageAdapter {
  save(file: { data: Buffer; kind: UploadKind }): Promise<{ url: string; thumbUrl?: string }>;
  remove(url: string): Promise<void>;
}
```

Реалізація одна — `LocalDiskStorage`: пише в `STORAGE_DIR`, express роздає цю теку статикою під
`/uploads`, ім'я файлу — uuid. Драйвер S3 на етапі 8 дописується під цей самий інтерфейс; це і є
причина, чому інтерфейс існує вже зараз.

**Конвеєр:** `multer` у пам'ять із лімітом 8 МБ → `sharp` визначає справжній формат із самих
байтів (заголовку `Content-Type` від клієнта не віримо) → зрізає EXIF, де лежить GPS зі шкільного
концерту → вписує в 1600px по довгій стороні → WebP q80. Для галереї додатково мініатюра 480px.

Фото з телефона на 6 МБ виходить приблизно 200 КБ. Без цього Lighthouse ≥ 90, здобутий на етапі 5,
не переживе першої ж реальної галереї.

Нові залежності API: `multer`, `sharp`. У `next.config` додається `images.remotePatterns` на хост
API. Нові змінні оточення: `STORAGE_DIR`, `PUBLIC_UPLOADS_URL`.

## 5. Екрани

Четверта група маршрутів `(admin)` з власним layout: щільні таблиці, форми, нуль декору — це
робочий інструмент, а не вітрина. Сесію, проксі, API-клієнт і дизайн-токени ділить із кабінетом.

`/admin` (лічильники: чернетки, заявки в групи, неоплачені абонементи, заняття сьогодні) ·
`/admin/teachers` + `[id]` · `/admin/directions` · `/admin/locations` · `/admin/prices` ·
`/admin/events` + `[id]` · `/admin/gallery` · `/admin/testimonials` · `/admin/achievements` ·
`/admin/pages` · `/admin/settings` · `/admin/schedule` · `/admin/subscriptions` · `/admin/groups` ·
`/admin/students`

Форми — серверні екшени в `app/actions/`, `FormState`, `Field`, `SubmitButton`: ті самі, що вже
працюють у кабінеті. Порядок сортування — числове поле й кнопки вгору/вниз: доступно з клавіатури
й не тягне бібліотеки.

Markdown для `SiteText` рендериться власною чистою функцією в `packages/shared` — абзаци, списки,
жирний, посилання — одразу в React-елементи, без `dangerouslySetInnerHTML` і без нових
залежностей. Чиста функція потрапляє рівно в ту категорію, яку розділ 9 базової спеки вимагає
тестувати.

## 6. Права

Три рубежі, кожен на своєму рівні:

1. `requireRole('ADMIN')` на префіксі `/admin` в API;
2. `/admin` у `PRIVATE_PREFIXES` проксі — щоб анонім не бачив каркаса сторінки;
3. перевірка ролі в `(admin)/layout.tsx`, і при невідповідності `notFound()`, а не редирект:
   сторінка, якої ти не маєш бачити, не повинна підтверджувати, що вона існує.

Токен запрошення живе 7 днів, одноразовий, зберігається хешем — як і решта в цій таблиці.

## 7. Тестування

**Інтеграційні:**

| Що                                                             | Навіщо                                            |
| -------------------------------------------------------------- | ------------------------------------------------- |
| Кожен адмінський маршрут: 401 аноніму, 403 викладачу            | табличний тест по списку — новий маршрут не пролізе повз охоронця |
| Наскрізне запрошення: створення → лист → пароль → вхід          | головний новий сценарій етапу                     |
| Вхід із `passwordHash = null` дає 401                           | найризикованіша правка схеми                      |
| Перемикач публікації змінює видачу публічного ендпоінта         | зв'язок адмінки з сайтом                          |
| Завантаження повертає посилання, за яким лежить файл; видалення прибирає | `StorageAdapter`                          |

**Юніт:** рендер markdown, рішення конвеєра обробки зображення, генерація імені файлу.

**Не тестуємо:** презентаційні компоненти — за розділом 9 базової спеки.

## 8. Порядок робіт

Обсяг великий, тому двома заходами в межах одного етапу:

1. **Наповнення сайту** — схема, `StorageAdapter`, викладачі, довідники, контент, тексти.
   Критерій готовності етапу («студія наповнює сайт без розробника») закривається тут.
2. **Операційка** — розклад, групи, абонементи, учні, бронювання за учня.
